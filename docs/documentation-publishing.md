# Documentation publishing and integrations

Proposed product direction; not a released plugin API.

One canonical executable feature, one normalized documentation model, multiple output surfaces. Keep presentation independent of test execution. The public Petstore reference is the only example; synthetic data only.

## Static guide
Title, description, prerequisites, actors, initial context, numbered task-oriented headings (step IDs and exact Gherkin retained), selected real screenshot after each meaningful action, results, related scenarios, optional ordinary video at the bottom. Provide a table of contents/anchors and accessible alt text. Use a capture checkpoint where possible; frames extracted from video must be labeled as such and linked to actual media offset, never fabricated. No mandatory custom player or client-side runtime. Missing or stale evidence must be visible. Group actions into readable sections without changing their order or introducing unverified instructions.

## Export architecture
Specification + run/case evidence -> normalized documentation model -> publication policy -> Markdown/MDX, standalone HTML, Studio, framework adapters. Normalize once; adapters map headings, metadata, screenshots, links, numbered steps, navigation and media components to host conventions. Generate offline from existing artifacts, not at site build by executing tests. Stable scenario IDs preserve routes through title/path changes. Keep manually authored docs separate from generated namespace. Incremental rebuild using source and evidence hashes; no overwrite of authored pages. Generic Markdown uses numbered headings and image links, with an ordinary video link fallback. MDX can use host-native steps and HTML video or a small accessible component.

## Integrations in order
1. Astro Starlight: generated Markdown/MDX content collection, native Steps component, sidebar and table of contents; optionally a thin integration/plugin. https://starlight.astro.build/manual-setup/ and https://starlight.astro.build/components/using-components/
2. Fumadocs: generated MDX collection/source, Steps component and native page tree; optionally a source adapter. https://www.fumadocs.dev/docs/mdx and https://www.fumadocs.dev/docs/headless/source-api
3. Docusaurus: generated docs folder and autogenerated sidebar, MDX component as needed. https://docusaurus.io/docs/sidebar/autogenerated
4. Other frameworks via generic Markdown/MDX exporter. Do not claim native plugin support until actual framework build and browser checks pass.

## Artifact delivery
Local relative assets first, then optional object store (S3-compatible) or CDN. Publication is a separate explicit action, never implied by recording. Publish only approved screenshot/video/subtitle assets, never raw run logs or snapshots by default. Store immutable versioned asset keys, MIME type, size, checksum, source run/attempt and scenario ID. Private default, authorized media delivery or short-lived signed URLs resolved at request time; avoid embedding expiring signed URLs in static builds. Public demo media only by explicit allowlist. Native video controls and poster, captions where calibrated, optional MP4 compatibility derivative preserving provenance and original WebM. Support range requests and correct content type. No external storage connection required for offline docs.

## Acceptance
Same Petstore scenario can render standalone HTML and a real Starlight site, then Fumadocs and Docusaurus. Verify generated links, responsive layout, native numbered steps, anchors, screenshot loading and video playback. No test run at site build and no external assets needed in local export. Verify missing/failed/stale artifacts and private/public policy. Keep guided and execution video roles distinct, with separate run/attempt identity; do not invent timing or mix results.
